# Fluid network staging (Forge 1.12.2 / Java 8)

This is deliberately **not a working fluid network** and must not be registered or offered to players as functional yet. The pipe/pump network does not extract, accept, store, insert, void or create fluid. The separate experimental tank can store fluid through its own handler, but is not connected to this network. `FluidPumpTile` is not `ITickable`, has no transfer/enable method and does not look up fluid capabilities. No world fluid blocks are touched by this network. The passive pipe is bufferless and has no `IFluidHandler`; there is no shared transfer interface with the separate tank implementation. Neither simulation nor an allowlist alone proves an atomic commit against arbitrary third-party handlers. A failing/reentrant handler can mutate then throw, refuse rollback, change identity, or invalidate a tile. Do not add a configuration switch that bypasses this restriction.

## Components

* `FluidPipeBlock`: bufferless passive block with six derived connection properties and no tile or NBT. Visual connections are to own pipes and pumps only, not tanks; they do not transfer fluid. `World` and the exact Forge `ChunkCache` are handled conservatively; unknown access wrappers remain disconnected. The staged multipart models use a core and six conditional arms. Entity collision uses the union of core and connected arms; ray targeting uses a custom union test, while the selection bounding box is an envelope. It is not an opaque/full rendering cube. These visuals, lighting, chunk boundaries and third-party renderers still require in-game review.
* `FluidPumpBlock`: horizontal `FACING` metadata (reserved output); opposite side reserved for input. Placement faces opposite the placer. One `FluidPumpTile`. The partial staged model has visual fittings, including side and bottom fittings, but these are not fluid connections. The block is not an opaque/full rendering cube; its collision remains a full cube.
* `FluidPumpTile`: intended for server-thread use, all sides expose receive-only FE, max 200 per call / 10,000 stored, simulation supported. Receipt checks for client, stale, unloaded, invalid, quarantined and reentrant use, but **neither capability access nor `live()` verifies the calling thread**. Do not assume cross-thread access is rejected or safe; getters and NBT paths are not a thread-safety boundary either. It rejects reentrant NBT reads/writes during receipt. A newly constructed or silently recreated tile starts quarantined; a genuine new placement explicitly initializes it, and a valid integer `Energy` on read restores it. Missing, wrongly typed or out-of-range data is quarantined and preserved verbatim on save, with charging disabled. Repeated NBT reads outside receipt/break are not prohibited and need lifecycle review. It has no FE consumption and cannot return FE, so charging is useless; forced removal can lose stored FE. It must remain unavailable in normal gameplay. It never pulls energy from neighbors. Dirty notification happens before and after a committed change; a failure after commitment is logged and returns the actual receipt. This is not a durable transaction: synchronous saves, crashes, world replacement and removals remain unresolved. A state change of the same block retains the tile through `shouldRefresh`; replacement by a different block does not.
* `PipeTopology.inspect(world, start, pipe)` performs optional bounded diagnostics on the server only, using loaded block states and the exact pipe block instance. It checks at most 256 connected pipes, aborts on an unloaded neighbor, over-limit or runtime error and returns zero for partial inspections. On COMPLETE, `distanceTo` returns the shortest pipe-edge distance from the initial pipe, or -1 if absent; all incomplete results return -1. The bounded snapshot retains no mutable caller position and has no transfer authority. It does not access tiles, capabilities, endpoints or intentionally load unloaded chunks. `COMPLETE` is only an observation, not permission to transfer; it can become stale immediately. Recompute after topology changes; do not persist its result.

## Removal and resources

The experimental pipe and pump unconditionally refuse the normal Forge player-removal callback, even when empty; their piston reaction is `BLOCK`, explosion drops are disabled, and their Forge explosion callback retains the block. The pump also attempts a best-effort server resync on refused player removal. These hooks do not cover commands, direct world replacement, bypassing mods or automation, earlier event/tool side effects, and crashes. No content-preserving removal or recovery is implemented. See `../tank/SAFETY.md` for the experimental tank and its separate limitations.

Staged blockstates, 3D models, item models, textures, proposed recipes and language fragments already exist under `src/fluidnetwork-staged-resources`, outside the active build. They are not evidence of a registered or playable feature. Pipe visual state and collision/ray behavior, and pump fitting orientations, have isolated/static coverage; actual Minecraft/Forge rendering, collisions, chunk load/unload and alternate renderers still need testing.

## To integrate later

Only after safety review and testing, register block instances, matching ItemBlocks and the pump TileEntity under stable unique names; review and integrate the staged resources, recipes and any UI separately. Registration is intentionally omitted. Do not silently release these placeholders. Before enabling transfers, coordinate with the tank implementation and design and verify an actual atomic transaction for the specific own tanks, including durable commit/recovery across saves/crashes, replacement/unload, sided access, reentrancy and failure injection. Generic Forge `IFluidHandler` must remain unsupported unless a real transaction protocol and validation exists. Clarify orientation, branch routing, cycle/alias prevention, volume/rate and FE cost only with that protocol. Prove no fluid duplication or loss, including tagged fluids and boundaries, under adversarial tests and an actual dedicated server; then revisit third-party compatibility explicitly. Resource/model and in-game tests are still required. Isolated Java 8/Forge regression and static checks do not constitute a full mod build, an in-game test or a crash-recovery test.
